# 游戏美术资源接入指南：给学生的 AI Agent

> 使用场景：学生已有一个基本可玩的游戏，希望在个人学习项目中改善界面美术；学生不需要会 Unity、团结引擎或 Photoshop。
>
> 本文是执行任务书。AI Agent 应完成项目检查、资源获取、素材整理、实际接入和验证，而不只是解释操作方法。
>
> 编写日期：2026-11-07。已读取老师提供的三个本地原包目录并计算 SHA-256；未在 Unity 中导入运行。版本号来自原文件名，PNG 数量为外层包路径计数，嵌套 PSD 包尚未逐个验证。所有资源均通过下列 GitHub Release 获取。

## 1. 学生怎样使用这份文档

在可以读取、修改游戏工程的 AI 编程工具中打开自己的游戏项目，把本文交给 Agent，并发送：

> 请按照这份文档，为我当前已有的游戏接入合适的 UI 美术资源。这是个人学习项目。请先判断项目技术栈、界面问题和资源适配程度，保留现有玩法与存档，不迁移引擎。优先完成一个真实页面和一组公共控件，再扩展到适合的界面。GitHub 下载遇到网络或权限问题时，告诉我最少需要做什么，并继续处理不依赖下载的工作。请实际修改和运行项目，给出前后对比及恢复方法。

可选补充，不填也应先开展项目检查：

- 我最想改善的页面：例如主菜单、游戏 HUD、结算页。
- 我喜欢的风格：例如明亮、轻松、简洁。
- 已下载文件位置：填写本机绝对路径；云端 Agent 则填写它实际能访问的位置。
- 已有课堂授权说明：可附老师统一提供的说明或文件位置，无需学生自行撰写；老师发放前填写第 12 节。

只有聊天能力、无法访问工程的 Agent，应明确能力限制，并提供可交接的任务记录。不能声称已经修改游戏。

## 2. 给 Agent 的任务边界

你的目标是：**用合适的真实素材改善当前游戏，而不是把游戏改成资源包的演示工程。**

执行原则：

1. 默认用于个人学习，不增加支付、广告、联网账号等原项目没有的功能。
2. 沿用现有引擎、框架、构建方式、场景组织和交互逻辑。资源包来自 Unity 商店，不代表项目必须改用 Unity。
3. 优先使用独立 PNG 和已有导出图；需要时解析图集、切片信息；PSD 和 Unity 编辑器属于后备方案。
4. 保留玩法、数值、输入、存档和页面流程。对 UI 做必要的小范围调整，不借换皮重写游戏。
5. 一套资源作为主风格。没有明显收益时，不把三套按钮、图标、阴影混在同一页面。
6. 用户未指定范围时，先处理主菜单或结算页，加按钮、面板、图标等公共控件；再覆盖关联页面与必要的 HUD 外观。不要自动改遍所有场景。
7. 常规本地检查、转换、接入、运行验证可直接推进。不要每一步都让新手决定文件格式、切图参数或代码结构。
8. 只有缺少必需信息、遇到账号操作、授权范围不明或需要重大玩法改动时才提一个明确问题；同时继续不依赖答案的工作。
9. 不自动购买素材，不发布项目，不上传素材到公开仓库，不把本地资源批量提交到第三方在线转换服务。
10. 没有实际下载、打开、接入或运行的步骤，必须标明“尚未完成”，不能以推测替代结果。

### 老师统一提供的授权信息

学生无需自行研究法律条款。老师应一次性说明：哪些学生可以取得、使用这些资源；是否允许提供整理后的文件；所用 AI 工具和处理方式是否在许可范围内。已有明确说明就沿用，不重复询问。学生自行合法取得资源且已有适用许可说明时，也可直接沿用，不要求提供购买凭据或订单隐私。

学习用途不自动赋予原始资源的再分发权。老师已明确声明取得本次三个原包的公开分发授权。Agent 沿用该声明，不重复向学生确认；素材原有使用范围仍适用，公开仓库不代表素材获得 MIT 等开源许可。参见 [Unity EULA 第 2 节](https://unity.com/legal/as-terms)。

授权信息缺失时，记录一次待补充项，先检查游戏、制定映射和整理通用脚本；需要授权的素材接入、模型上传暂缓。不要把“已下载到本地”当成“可以输入任何云端 AI”的依据。

## 4. 总体流程与恢复点

按以下顺序推进，每个阶段更新一份简短的 `asset-integration-report.md`。中断后读取该文件继续，不必重做。

| 阶段 | 应完成的动作 | 进入下一阶段的依据 |
| --- | --- | --- |
| 0 项目检查 | 找到工程、启动方式、UI 入口，保留改动前基线 | 已知修改哪里、如何运行和恢复 |
| 1 获取文件 | 使用本地文件或下载，核验格式与来源 | 获得真实可读取的资源文件 |
| 2 资源分析 | 解包、分类、预览、记录切片和来源 | 找到适合本项目的素材 |
| 3 页面试接入 | 一个真实页面和一组公共控件 | 页面能操作，视觉与功能均通过检查 |
| 4 扩展接入 | 应用到约定范围内的其他 UI | 样式一致，主要游戏流程正常 |
| 5 交付 | 前后对比、文件清单、验证结果、恢复方式 | 学生能直接体验成果 |

状态必须区分 `完成`、`进行中`、`受阻`、`不适用`；不要把“有方案”写成“已接入”。

## 5. 阶段 0：先理解学生已经做好的游戏

先读取项目自身说明、Agent 指令和构建配置，再检查文件与界面。不要直接假定是 Unity 项目。

| 工程线索 | 可能的技术栈 | 应优先确认 |
| --- | --- | --- |
| `package.json`、网页入口 | HTML/CSS、React、Phaser、PixiJS、Three.js 等 | 实际 UI 是 DOM、Canvas 还是引擎 UI |
| `project.godot` | Godot | 版本、Control/Theme、场景和导入规则 |
| `assets`、Cocos 项目配置 | Cocos Creator 等 | 版本、场景、SpriteFrame、资源加载方式 |
| `Assets`、`ProjectSettings`、`Packages` | Unity 或团结相关工程 | 准确引擎与版本、UGUI/UI Toolkit、现有依赖 |
| 只有可执行文件或在线试玩链接 | 不一定有源工程 | 是否具备修改源码和资源的入口 |

这些只是线索，目录名不能单独证明技术栈。一个工作区有多个游戏时，只修改用户指定的工程；不能确定才询问目标路径。

必须完成：

- 检查工作区现有修改，保护学生未提交的成果；无版本管理时备份将要改动的文件。不要执行整体清空、强制回退或覆盖。
- 尝试运行原项目，记录启动命令、主要界面、现有报错；原有错误与本次新增错误分开记录。
- 能截图就保存相同尺寸的改动前截图。不能截图时明确说明，不伪造对比。
- 列出 3～5 个最有价值的 UI 改善点，例如按钮大小混乱、弹窗边框失真、图标风格不统一。
- 检查玩法区占用、触摸/鼠标输入、横竖屏、画面尺寸、中文字体和关键页面流程。
- 给出简短选择结论：主资源包、优先页面、预计使用的组件、需要保留的现有视觉。

如果三套资源都不适合，比如现有游戏强调像素画或暗黑写实，可只使用风格兼容的少量元素，或者明确说明不宜整体换皮。不要为了展示素材而破坏原有风格。

## 6. 阶段 1：通过 GitHub 获取资源

### 6.1 获取顺序

1. 优先使用已经下载且 SHA-256 匹配的本地文件。
2. 读取 `resources.json`，选择一个合适的资源，通过对应 `downloadUrl` 下载。
3. 直链失败时打开 [Release 页面](https://github.com/LiLiShader/game-ui-learning-resources/releases/tag/classroom-2026-11-07)，在 Assets 中找到同名 `.unitypackage` 附件。

不必克隆整个仓库；克隆代码或下载 Source code ZIP 不会得到 Release 附件。下载工具必须跟随 HTTPS 重定向，先保存为 `.part`，完整下载并验证哈希后再改为最终文件名。网络中断可使用受支持的断点续传，服务器不支持时重新下载。

命令示例（从清单填入真实值，并正确引用路径）：

```sh
curl --fail --location --retry 3 --continue-at - --output "资源文件.unitypackage.part" "从 resources.json 取得的 downloadUrl"
```

Agent 应用 Python `hashlib.sha256` 或系统等价工具核对清单中的哈希；不匹配时禁止继续解包。不要对原文件做修复后仍使用原哈希。

### 6.2 网络和权限问题

- 公开期间通常无需 GitHub 登录。不能将 HTML 错误页、访问拒绝页、未完成文件当作资源包。
- 若仓库后续转为私有，匿名直链将无法继续使用；请有访问权限的学生使用自己的 GitHub 登录下载，或使用已经校验过的本地副本。不要把 404 一律当成文件删除。
- 不索取学生密码、访问令牌或 Cookie。需要登录时，让学生在自己的界面完成。
- 使用云端 Agent 时，本机下载文件不会自动进入云端工作区；通过工具支持的工作区上传方式交接。
- 下载受阻时继续项目检查和素材映射准备，不无限重试。

最小人工交接模板：

> 当前 GitHub 下载遇到【具体错误】。请打开上方 Release 页面，在 Assets 中下载【准确文件名】，放入项目 `resource-inbox/` 或告诉我实际路径。无需安装 Unity，也不用先解压。我会继续处理不依赖素材的项目检查。

### 6.3 下载核验与保存

记录实际下载 URL、时间、字节数和 SHA-256，并与本指南/清单比对。原包保持不变，各包独立存放。打开前检查真实格式；解压时校验路径、符号链接、展开体积和磁盘空间，不执行包内未知脚本。

## 7. 阶段 2：不会 Unity 也能处理资源

### 7.1 先判断文件类型

| 实际拿到的文件 | 首选操作 | 是否需要 Unity |
| --- | --- | --- |
| 独立 PNG/WebP/JPG | 读取图片、分类、选择所需文件 | 不需要 |
| PNG ZIP / 普通 ZIP、7z、RAR | 安全解压，再检查内部文件 | 通常不需要 |
| `.unitypackage` | 根据内部路径还原源文件及 `.meta` | 提取常见源图通常不需要 |
| PSD/PSB | 先找同包 PNG；缺少必要元素再导出 | 不需要 Unity，可能需要图像工具 |
| PNG 图集和 `.meta` / JSON | 按真实切片信息拆图或接入图集 | 通常不需要 |
| `.prefab`、`.unity`、`.mat` | 在适用许可下读取布局/引用线索 | 非 Unity 项目不能直接运行这些文件 |
| Godot/Unreal 对应文件 | 项目引擎与版本匹配时再考虑 | 不需要 Unity |
| AssetBundle、编译后纹理或不明二进制 | 优先获取源图或标准包，报告限制 | 不承诺无编辑器转换 |

无需把所有格式全部转换。目标是获得项目实际需要的、可验证的素材。

### 7.2 `.unitypackage` 的还原规则

常见 `.unitypackage` 是 gzip 压缩的 tar 容器。不要仅改扩展名当 ZIP；先验证文件实际格式。

常见内部记录形态如下，这是结构示例，不是本次资源的实际清单：

```text
<guid>/pathname
<guid>/asset
<guid>/asset.meta
<guid>/preview.png
```

Agent 可使用 Python 标准库 `gzip` 和 `tarfile` 编写本地提取工具。本次检查中，第二、第三个包直接使用 `tarfile.open(..., "r|gz")` 遇到读取错误，改为 `gzip.open` 后交给 `tarfile.open(fileobj=..., mode="r|")` 可读取。按以下要求实现：

1. 先枚举普通文件记录，将同一 GUID 下的文件分组；限制成员数和累计展开字节数。
2. 读取 `pathname`，得到原相对路径。本次 Simple Casual 与 Minimal Game Light 的路径记录均出现 `\n00` 尾部；识别并记录该格式后仅将第一行作为路径，不能把换行与 `00` 写进文件名。未知尾部应报错，不盲目截断任意多行路径。
3. 在新建的独立输出根目录内，把 `asset` 保存为该路径，把 `asset.meta` 保存为该路径加 `.meta`。
4. 不把 `preview.png` 当作正式美术素材；它可能只是编辑器预览。
5. 目录记录可能只有路径和 `.meta`，没有 `asset`；核对 `folderAsset: yes` 等明确目录证据后按目录处理。缺少 `asset` 本身不足以证明是目录；指向 PNG/PSD 等文件却无内容时，记录为不完整条目。
6. 对 tar 成员名及 `pathname` 都校验；拒绝绝对路径、盘符、`..`、符号/硬链接以及解析后落到输出目录外的路径。
7. 检查重复路径、大小写冲突和已有文件，不静默覆盖。保留包 ID、GUID 与输出路径映射。
8. 输出提取成功、跳过、冲突和失败数量；脚本可重复执行但不能破坏原文件。

这是常见容器处理方案，不保证覆盖每种打包形式。实际结构不符时记录样本特征并换路线，不硬猜。提取源 PNG 不会自动复制 Unity 渲染效果或还原 Prefab 功能。

### 7.3 保留 `.meta`，重点处理九宫格和图集

`.meta` 不只是可删的杂项：它可能记录 GUID、切片、边框、轴心及导入设置。[Unity 元数据说明](https://docs.unity3d.com/2022.3/Documentation/Manual/AssetMetadata.html)

跨引擎时把 Unity `.meta` 留在分析目录，将所需信息转换为目标格式；不要直接复制去覆盖 Cocos 等引擎自己的同名 `.meta`。Unity 项目则保持资源与原 `.meta` 配对，并检查 GUID 冲突。

检查真实字段和版本，不用简单正则把所有 YAML 当成一种结构：

- `spriteMode`：单图或多 Sprite。
- `spriteBorder` / 每个 Sprite 的 `border`：九宫格边界。
- `spriteSheet.sprites`：可能包含名称、矩形、轴心、边框。
- `spritePixelsToUnits`、过滤方式等：作为原始信息记录，不直接当目标引擎的尺寸。
- Prefab 中的颜色、图片类型等：白色底图可能依赖运行时染色，PNG 本身不是最终效果。

**图集裁切坐标：**对于使用左下原点的 Unity Sprite 矩形 `(x, y, w, h)`，原图高度为 `H`，转为常见左上原点裁切框：

```text
left   = x
top    = H - y - h
right  = x + w
bottom = H - y
```

必须验证坐标在图内，并抽查裁切结果。如果另有旋转、裁边或外部图集描述，按其真实格式处理，不能强套上述公式。[Unity Sprite 矩形](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Sprite-rect.html)

**九宫格边框顺序：**Unity `Sprite.border` 为左、下、右、上；CSS `border-image-slice` 为上、右、下、左。统一存成显式对象 `{left, top, right, bottom}`，再转为目标引擎格式，避免顺序误用。源图切片像素与界面实际显示边框宽度分开记录，不能把高分辨率素材的像素值直接当 CSS 显示尺寸。[Unity Sprite.border](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Sprite-border.html)

按钮和弹窗边框优先使用九宫格；保留角部尺寸，伸缩中间区域。缺失边框数据时可通过图像分析估计，但必须标注“估计值”并做不同尺寸的实际验证。不要机械地把图片三等分，也不要连文字、图标一起拉伸。

若裁掉透明留白，需要同步修正裁切矩形、九宫格边界、轴心或布局偏移；默认保留原留白更稳妥。

### 7.4 PSD 处理策略

1. 同包已有合适 PNG，就先用 PNG；不要为了“使用 PSD”制造额外工作。
2. 需要某个元素而 PNG 缺失时，检查图层组、可见性、边界、蒙版和图层样式。不要把整张 UI 示意图当作按钮或完整功能界面。
3. 本地可用 `psd-tools` 等工具尝试合成与导出；创建隔离依赖环境，不要求学生先购买 Photoshop。
4. 复杂混合、文字、智能对象和图层效果可能不能准确还原；对比原始合成预览，检查透明边缘、阴影和颜色。失败时优先回到现成 PNG，必要时才使用可用的图像编辑器。
5. 默认本地处理；使用在线编辑或云端 AI 前必须已有对应上传权限。不能因为在线工具更方便就自动上传整个源文件。
6. 图层不能拆分就如实说明。用运行时文本显示中文、金额和分数，不把所有文字烘焙到图片中。

PSD 自动合成并非 Photoshop 的完整替代，具体限制见 [psd-tools 官方文档](https://psd-tools.readthedocs.io/en/latest/)。

### 7.5 必要时才使用 Unity 作为导出工具

只有需要 Unity 导入或渲染才能得到目标素材、现成 PNG 与普通提取都不足时，才考虑此路线。本机已有兼容编辑器时，使用独立临时工程，只导入检查过的必要文件和依赖，由 Agent 准备最小导出工具；不运行包内未知编辑器脚本，不向学生原项目整体导入 Demo。核验导出图后，仍回到原技术栈接入。

本机没有编辑器时，优先让老师提供 PNG 或已导出的文件，不自动安装大型引擎。确实必须安装时先说明原因、预期体积和替代方案。材质、动画或依赖无法还原时，如实记录限制，不承诺一键转换所有 Unity 资源。

## 8. 把素材整理成 Agent 能准确使用的目录

以下是建议逻辑结构，可按现有工程习惯调整；不要强迫项目采用新的框架或打包规则。

```text
resource-inbox/                    # 原始下载，私有，本地保留
asset-work/
  extracted/<pack-id>/             # 还原文件和原始 meta
  previews/<pack-id>/              # 分类缩略图/本地素材目录
  asset-inventory.json             # 实际资源清单
  asset-integration-report.md      # 决策、进展、验证与恢复记录
<现有项目素材目录>/ui/<theme>/      # 仅复制被使用的运行时素材
<现有配置位置>/ui-asset-map.json    # 或项目合适的 TS/资源配置
```

原包、PSD、全部提取文件和素材预览不进入运行时构建。按项目规则排除不应提交的源资源；注意 `.gitignore` 对已跟踪文件无效，也不等于发布目录已排除。公开源代码使用占位资源与本地恢复步骤，不能顺手提交付费原图。

### 8.1 资源清单与可视化索引

清单至少记录：包 ID、相对路径、格式、尺寸、透明通道、文件哈希、用途候选、GUID（有则填）、原图/切片关系、九宫格、轴心、是否采用及理由。

用本地图像工具生成分类缩略图，给每张图加索引号和文件名；透明素材放到能看清的中性底色或棋盘格上。数量多时分页，并挑选候选素材放大查看。不要一次把上千张图塞进一张无法辨认的预览。

在已确认允许的 AI 工作流中查看预览。若模型没有视觉能力或不允许接收图片，就保留本地预览供学生选择，并坦率标注判断依据只是文件名、尺寸或人工选择。

既要看文件名，也要核对实际图像。检查白色可染色底图、多分辨率重复项、按钮状态和特殊背景，避免用错图。

### 8.2 语义映射，避免业务代码依赖混乱文件名

先根据游戏功能定义稳定语义键，再绑定真实素材，例如：

| 语义键 | 游戏中的作用 | 渲染策略 |
| --- | --- | --- |
| `button.primary.normal` | 开始、确认等主要操作 | 九宫格底图 + 原有文本和事件 |
| `button.primary.pressed` | 按下反馈 | 包内状态或运行时颜色/位移 |
| `panel.dialog` | 暂停、结算窗口 | 面板与内容分层，必要时九宫格 |
| `icon.close` | 关闭当前窗口 | 独立图片 + 原有可点击控件 |
| `bar.health.fill` | 现有血量显示 | 按真实数据裁切/填充 |

这里的语义键是示例，不说明资源包一定存在同名文件或这些状态。没有合适素材时保留现有样式或用程序补充，并注明。

映射记录格式示例（`null` 必须依据实际检查填写，不可据此声称已完成）：

```json
{
  "theme": "pending-selection",
  "assets": {
    "button.primary.normal": {
      "packId": null,
      "sourcePath": null,
      "runtimePath": null,
      "sourceSha256": null,
      "sourceSize": null,
      "sourceRectTopLeft": null,
      "nineSlicePx": null,
      "tint": null,
      "status": "unresolved"
    }
  }
}
```

九宫格数据用 `{ "left": 0, "top": 0, "right": 0, "bottom": 0 }` 形态，数值必须来自检查；零表示实际没有边框，未知不能填零冒充有效值。转换后记录源路径、输出路径、操作和参数，保证能追溯和重复生成。

## 9. 阶段 3～4：接到学生现有游戏，而不是只做素材展示

### 9.1 根据真实 UI 系统选择路线

| 现有项目 | 接入办法 | 重点检查 |
| --- | --- | --- |
| HTML/CSS/React/Vue | 用图片、背景、CSS 九宫格或分层组件；保留原按钮和回调 | 中文文字、响应式、焦点、加载路径 |
| Phaser/PixiJS/Canvas | 接入现有加载器；用该版本支持的九宫格/裁切/填充实现 | 命中区、缩放、图层、输入事件与纹理生命周期 |
| Three.js / 其他 3D 游戏 | UI 原本为 DOM 时复用 DOM；原本为游戏内 UI 时沿用该系统 | UI 不遮挡游戏、不意外拦截镜头和操作输入 |
| Godot | 复用 Control、Theme、TextureRect/NinePatchRect 等适用机制 | 锚点、容器、伸缩与鼠标过滤 |
| Cocos Creator | 按版本导入图片和 SpriteFrame，使用切片/填充功能 | 元数据格式、UUID、异步加载与释放 |
| Unity/团结 | 先隔离检查资源和兼容性，再把所需部分接入既有 UI | 版本、引用、字体、依赖、现有回调 |
| 其他技术栈 | 寻找该系统的图片、九宫格、字体与控件机制 | 不为使用这套资源而换框架 |

核对工程安装版本和对应官方文档后再写 API；表格是路线建议，不能代替版本检查。若现有引擎已支持所需能力，不增加新 UI 框架。

非 Unity 工程不直接运行 `.prefab` 或 C# 脚本。只重建当前项目需要的外观和布局；Demo 中有商店、排行榜、装备页，不代表当前游戏要新增这些系统。

### 9.2 三种改造深度

- **轻量换皮，默认优先：**替换按钮底图、面板、常用图标、进度条；尽量保持布局与事件不变。
- **局部优化：**原布局阻碍效果时，调整一个页面的间距、层级、尺寸和适配；仍保留原功能流程。
- **大范围重做：**仅当用户明确要求且已有理由时采用。不要因为资源包有完整演示页，就自动重建整个游戏 UI。

### 9.3 先做一个真实页面，再批量扩展

1. 选可代表风格且风险较低的现有主菜单或结算页。
2. 接入约 5～10 个实际需要的素材或组件，不以数量为硬指标。
3. 建立统一的按钮、面板、图标尺寸和文字样式；默认只用一种主风格。
4. 保留 normal、pressed、disabled、selected、focus 等项目需要的状态。触屏项目不依赖 hover 才能理解操作。
5. 真正点击开始/返回/重试，确认还连接原游戏逻辑。
6. 通过检查后，自主扩展到任务范围内的公共 UI；无需等待学生逐个批准图标。

### 9.4 视觉适配细节

- 图片负责装饰，文字负责信息，交互由原有控件承担；不要把整个页面做成一张无法操作的图片。
- 文字、按钮底图、图标和点击区域分开控制。长中文、动态分数和数值不能挤出容器。
- 优先沿用覆盖中文且已获许可的字体；包内字体不一定有中文字形。不要因缺字擅自下载不明字体。
- 白色素材可能需要染色才能接近示例效果；不要误判为资源损坏。
- 横屏游戏参考资源风格即可，按横屏重新排版，不能整张拉伸竖屏示意图。
- 面板使用九宫格时检查最小尺寸、角部是否变形、中心是否需要填充。
- 图标按显示尺寸和设备像素比选择分辨率；无需把所有图标都用最大尺寸，也不要放大低分辨率图后声称清晰度提升。
- 暂停窗口、遮罩、提示和 HUD 注意层级；装饰层不应该阻挡按钮或玩法区输入。
- 在确认必要后再做图集、缩放或格式压缩；UI 细线、文字和透明边缘优先保证清晰。
- 只为已存在的交互补充必要反馈，不重写玩法或加入 Demo 的虚构数据。

## 10. 阶段 5：必须验证的内容与交付物

### 功能验证

- 原项目适用的构建、类型检查或已有测试通过；记录命令和结果，不盲目新增大量测试。
- 至少完成一次“进入游戏 → 正常游玩 → 暂停/返回 → 结算或重试”的实际流程，按项目支持的功能调整。
- 核对鼠标/触摸和项目原本支持的键盘或手柄输入。
- 存档、分数、道具等业务数据没有因 UI 改动丢失或被 Demo 数据替换。
- 无新增资源 404、路径大小写错误、纹理缺失和未处理加载错误。

### 视觉与负载验证

- 同状态、同视口保存前后截图；检查主页面、一个弹窗和一个玩法中界面。
- 若项目承诺多端适配，至少检查实际目标范围内的一窄一宽两种视口；固定分辨率项目按其设计检查，不强制改变产品定位。
- 检查九宫格、文字溢出、透明边缘、图标模糊、状态辨识和遮挡问题。
- 记录实际引入图片数、总字节数，以及能测到的加载/运行变化。没有测量就不写“性能无影响”。
- 检查生产构建的资源路径与本地开发不同的情况，例如部署子目录和大小写敏感环境。
- 确认原包、PSD、临时预览和未使用素材没有被无意打进交付包。

### 交付给学生

1. 已修改并能运行的游戏，或者明确列出尚未解除的阻塞。
2. 简短说明：用了哪套素材、改善哪些页面、如何启动。
3. 前后对比截图及所在路径；无法截图/运行时明确说明替代检查和未验证项。
4. 实际素材清单、语义映射和转换记录。
5. 修改文件清单和恢复办法；仅恢复本次变更，不覆盖学生其他工作。
6. 后续可改进项，和“本次已完成”严格分开。

禁止用“已下载”“已解压”“已生成素材浏览页”代替“已接入游戏”。如果任务被阻塞，应交付已完成的项目检查和接入准备，并明确下一步需要的唯一关键输入。

## 13. 给 Agent 的最终启动指令

读完本文，立即从阶段 0 开始。先确认真实工程和已有 UI，再选择资源。优先找可直接使用的 PNG；必要时还原 `.unitypackage`，结合 `.meta` 做正确切片和九宫格。用语义映射接入一个真实可操作页面，验证后扩展。GitHub 下载受阻时做最小人工交接，并继续独立工作。最后提供实际运行结果、素材来源、对比和恢复方式。

**本次任务的完成标准是学生已有游戏的界面得到可验证的改善，而不是学生学会操作 Unity，也不是电脑上多了一个素材压缩包。**
